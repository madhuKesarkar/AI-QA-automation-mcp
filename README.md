# QA Automation — Linear + Playwright MCP

Sprint QA automation pipeline: features move to "Ready for QA" in Linear →
context is pulled from PRD/FE spec/BE spec/Figma → a tagged Gherkin test plan
is drafted and reviewed → Playwright MCP generates scripts against the live
staging app → tagged suites run in CI → results post back to Linear.

See the full process doc: `qa-automation-sop-linear-playwright-mcp.md`
(kept alongside this repo, not inside it, since it's a living process
reference rather than code).

## Agent orchestrator

The manual process above (Claude in Chrome, hand-reviewed selectors) is
how this repo's coverage was actually built. `agent/` contains an
autonomous version of the same pipeline, driven by Linear labels and split
into two stages:

- **"ready for QA"** runs the planning pipeline — consolidate requirements
  from the ticket and its linked docs, then draft tagged Gherkin + a
  test-plan table — and stops at a human plan-approval gate.
- **"ready for QA execution"** runs the execution pipeline — execute the
  scenarios against Sandbox and QA, classify any failures as
  product-bug / env-flakiness / test-issue, and post the results back to
  the ticket.

Human gates at plan approval and at first-time selector/session capture are
non-negotiable. See `agent/README.md` for the full five-agent design and
honest limitations before relying on it.

## Structure

This repo holds two sub-projects: the **test suite** (root, documented
here) and the **`bw-qa-loop` agent orchestrator** (`agent/`, its own npm
package — see `agent/README.md`).

```
tests/                       ← THE TEST SUITE (this README)
  features/        Gherkin .feature files — one per feature, human-and-agent-editable
    bulk-upload-rates-single-site.feature
    bulk-upload-rates-single-site.md   ← test case table + traceability, the durable record
  steps/            Step definitions (glue code), reused across features
    bulk-upload-rates-single-site.steps.ts
  fixtures/         Seed data / API helpers for Given steps that need setup
playwright.config.ts
package.json                 Root package: Playwright + playwright-bdd deps, test scripts
.github/workflows/qa.yml     CI: smoke+sanity on PRs, full suite nightly

agent/                       ← THE ORCHESTRATOR (see agent/README.md)
  README.md         Full five-agent design, label triggers, human gates
  package.json      Nested package "bw-qa-loop" (type:module, own deps)
  src/              Two pipelines: requirements-reviewer → test-planner →
                    [plan gate] → executor → bug-analyser → status-reporter
  bin/bw-qa-loop    Launcher (runs the pipeline inside a Docker sandbox)
  selector-registry.json   Known, human-verified selectors reused across tickets
```

`tests/.features-gen/` is generated by playwright-bdd at test-run time and
is gitignored — never edit it directly.

## Tagging convention

- `@smoke` — is the build usable at all
- `@sanity` — does this specific feature work at a basic level
- `@functional` — full validation: edge cases, validation errors, states

## Running locally

```bash
npm install
npm run install:browsers   # first time only, downloads Chromium
export BASE_URL=https://schools.qa.bwtest.net   # or your staging URL

npm test                # full suite
npm run test:smoke      # smoke only
npm run test:sanity     # sanity only
npm run test:functional # functional only

npm run report          # opens the last HTML report
```

## Adding a new feature's tests

1. Copy the pattern in `tests/features/bulk-upload-rates-single-site.feature` —
   one `.feature` file per feature, named `<feature-slug>.feature`.
2. Add a matching `<feature-slug>.md` with the test case table and
   source references (PRD section, Figma frame, or "verified against live
   app" if there's no written spec) — this is what makes the suite
   auditable later. Never invent a scenario you haven't confirmed against
   either a spec or the real app; flag it as an open question instead.
3. Add/reuse step definitions in `tests/steps/`.
4. Get the plan (`.md` + `.feature`) reviewed and approved before wiring
   it into CI — see the SOP's review-gate step.

## CI behavior

- **Pull requests:** runs `@smoke` + `@sanity` only, for fast feedback.
- **Nightly (2am UTC) + manual dispatch:** runs the full suite including
  `@functional`.
- Reports are uploaded as build artifacts. For sprint-level trend tracking
  (flaky tests, coverage over time), see the SOP's reporting section —
  Allure or Currents.dev are the two lighter-weight options.

## Requires

- `STAGING_URL` (or `BASE_URL` locally) — a stable, seeded staging
  environment. Flaky/unseeded environments will produce flaky
  MCP-generated tests regardless of how good the scripts are.
- Components should carry `data-testid`s where role-based locators aren't
  reliable — ask FE to add these on new components.
