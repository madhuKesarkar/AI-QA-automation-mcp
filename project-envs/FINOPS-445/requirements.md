## Requirements

## 1. Feature Overview & Scope

**1.1** The Bulk Raise Rates feature allows school admins to bulk-adjust rates on existing billing plans (Flow A) and on plan templates with optional cascade to downstream plans (Flow B), without editing each plan one at a time.
*Sources: BE Tech Spec §1, FE Tech Spec §1*

**1.2** Both flows apply changes immediately (no scheduling in v1) to not-yet-posted future charges. Posted invoices are never retro-updated.
*Sources: BE Tech Spec §4.7, FE Tech Spec §1, §4.1*

**1.3** Both entry points are gated behind a single FlagSmith feature flag: `billing_bulk_raise_rates`. Rollback = flip the flag.
*Sources: FE Tech Spec §2, FE Execution & Rollout Plan*

**1.4** Flow A entry point: Students › Student plans table, via a new "Edit plan rates" option in the existing "Select an action" dropdown (enabled when ≥1 row is checked).
*Sources: FE Tech Spec §3.1*

**1.5** Flow B entry point: Library › Bill plan templates table, via a floating bottom action bar showing `{N} of {M} × Edit template rates` (appears when ≥1 template is checked).
*Sources: FE Tech Spec §3.2*

**1.6** Access control: Admin and Billing Only roles can use both flows. Staff and Parent/Payer roles cannot.
*Sources: PRD Access Control section*

**1.7** Web only (no mobile).
*Sources: PRD Out of Scope*

## 4. Adjustment Math & Business Rules

**4.1** Adjustment types:
- `kind: percent`: `value` is signed percentage points (e.g., `value: 5` = raise 5%). Applied proportionally to all eligible `RecurringCharge.original_amount` values on the plan.
- `kind: flat`: `value` is signed canonical integer cents (e.g., `value: -2500` = lower $25). Flat values are NEVER sent as dollar-unit floats.
*Sources: BE Tech Spec §1.1, §3.1; FE Tech Spec §1.1, §3.3*

**4.2** Flat adjustment on multi-charge plans: the entire flat delta is applied to the single largest eligible charge per plan (first-wins on tie). Only ~8% of templates have multiple charges.
*Sources: BE Tech Spec §4.8; FE Tech Spec §4.4*

**4.3** Percent adjustment on multi-charge plans: applied proportionally to all eligible charges.
*Sources: FE Tech Spec §1, §4.4*

**4.4** Eligibility for adjustment: every active `RecurringCharge` that is rate-bearing. Discount and credit rows are excluded and are NEVER directly adjusted.
*Sources: BE Tech Spec §3.1*

**4.5** After adjusting a rate-bearing charge's `original_amount`, `CorrectDiscountedAmount` recomputes `amount` so existing per-plan discounts are preserved unchanged.
*Sources: BE Tech Spec §3.1, §4.2*

**4.6** Split-payer plans: the increase applies to the total charge; payer split percentages are unchanged; the new total is redistributed proportionally.
*Sources: PRD BR-01*

**4.7** Zero or below-zero resulting amounts: if an adjustment would result in a non-positive amount for a plan, that plan is skipped with reason `non_positive_resulting_amount`.
*Sources: BE Tech Spec §3.1; FE Tech Spec §4.6*

**4.8** A 0% or $0 adjustment value is invalid; the "Next" button remains disabled until a non-zero value is entered.
*Sources: PRD BR-09; FE Tech Spec §3.1*

**4.9** Effective date: immediate only in v1. Posted invoices are never retro-updated. Existing unposted, unskipped invoices tied to the plan are updated when the recurring charge changes (via `UpdateRecurringChargeService`). Future unposted invoices use the updated rate at post time.
*Sources: BE Tech Spec §4.2, §4.7*

**4.10** Cascade uses delta cascade only (not snap cascade): the same signed adjustment is applied to each downstream recurring charge regardless of drift, preserving per-plan customizations.
*Sources: BE Tech Spec §4.3, §4.6*

## 5. Backend API Contract

**5.1 Flow A endpoints:**
- `POST /api/v2/billing/plans/bulk_adjust_charges_jobs`
- `GET /api/v2/billing/plans/bulk_adjust_charges_jobs/:id`

*Sources: FE Tech Spec §3.3; BE Tech Spec §3.1*

**5.2 Flow A request payload:**
```json
{
  "plan_ids": ["..."],
  "adjustment": { "kind": "percent|flat", "value": 5 },
  "dry_run": false
}
```
*Sources: FE Tech Spec §3.3*

**5.3 Flow B endpoints:**
- `POST /api/v2/billing/plan_templates/bulk_adjust_charges_jobs`
- `GET /api/v2/billing/plan_templates/bulk_adjust_charges_jobs/:id`
*Sources: FE Tech Spec §3.3*

**5.4 Flow B request payload:**
```json
{
  "template_ids": ["..."],
  "adjustment": { "kind": "percent|flat", "value": 5 },

  "cascade_target": { "plan_ids": ["..."] },
  "dry_run": false
}
```
`cascade_to_existing_plans` defaults `false`. `cascade_target` is optional and is a filter only (not an alternative root target).
*Sources: FE Tech Spec §3.3; BE Tech Spec §3.2*

**5.5 Both endpoints are async** (Sidekiq job extending `EphemeralReport`). POST returns `{ id, status, result, error }`. Client polls the GET endpoint.
*Sources: BE Tech Spec §2; FE Tech Spec §3.3*

**5.6 Dry-run and apply use the SAME endpoint**, differing only by the `dry_run` flag. Dry-run is idempotent — persists nothing.
*Sources: BE Tech Spec §3.1; FE Tech Spec §1.1, §3.3*

**5.7 Response shape (core — same for dry-run and persisted):**
```json
{
  "dry_run": true,
  "target_type": "plans|templates",
  "summary": {
    "requested_count": 100, "eligible_count": 94, "updating_count": 92, "skipped_count": 8,
    "current_total_cents": 12000000, "projected_total_cents": 12600000,
    "net_delta_cents": 600000, "net_delta_pct": 5.0
  },
  "changes": [...],
  "skipped": [{ "plan_id": "uuid", "reason": "non_positive_resulting_amount", "message": "..." }],
  "execution": null
}
```
Persisted runs (`dry_run: false`) populate `execution`:
```json
{ "execution": { "succeeded_count": 92, "failed_count": 0, "persisted_at": "...", "audit_request_uuid": "uuid" } }
```
*Sources: BE Tech Spec §3.1; FE Tech Spec §3.3*

**5.8 Flow B cascade response** includes a nested `cascade` object:
```json
{
  "cascade": {
    "summary": { ... },
    "selected_count": 175, "not_selected_count": 0,
    "drifted_plans_count": 20, "drifted_plans_cascaded": 20,
```

## 6. Job Polling & Apply Lifecycle

**6.1** FE polls at 1-second intervals up to 30 seconds max (`GET .../:id`). The job persists its result server-side for 7 days (`PERSIST_RESULT_FOR = 7.days`) regardless of whether the FE is still polling.
*Sources: FE Tech Spec §3.3, §4.8*

**6.2** On `status=complete` (within 30s): modal closes and a minimal Snackpack toast reports the outcome (see §7).
*Sources: FE Tech Spec §3.1, §4.8*

**6.3** On job error (`status=errored` or no job created): error toast: "Couldn't update rates. Please try again." Safe to retry — nothing was persisted.
*Sources: FE Tech Spec §4.8*

**6.4** On timeout (30s elapsed, job still running): modal closes with a non-error inline note: "This is taking longer than usual. Your changes are still processing and will appear in the plans table shortly." No retry option is shown. A retry here would re-POST and double-apply the rate change.
*Sources: FE Tech Spec §4.8*

**6.5** During polling, a spinner/processing state is shown in the modal. Figma confirms a "Processing your updated rates / This can take a bit - hold tight!" modal state exists.
*Sources: FE Tech Spec §4.8; Figma metadata*

## 10. Backend Processing Details

**10.1** Operations are async Sidekiq jobs extending `EphemeralReport`. Workers: `Billing::AdjustRatesOnPlans` (Flow A) and `Billing::AdjustRatesOnTemplates` (Flow B). Per-plan transactions. School-scoped.

*Sources: BE Tech Spec §4.2*

*Sources: BE Tech Spec §3.2, §4.1*

**10.5** Cascade lookup uses `recurring_charges.billing_library_charge_id` FK (after backfill) or falls back to `(name, billing_category_id)` heuristic match if FK is absent.
*Sources: BE Tech Spec §4.4*

**10.6** A new partial index is required for cascade: `CREATE INDEX CONCURRENTLY index_recurring_charges_on_billing_library_charge_id ON recurring_charges (billing_library_charge_id) WHERE billing_library_charge_id IS NOT NULL`.
*Sources: BE Tech Spec §3.3*

**10.7** After cascade, the FK on downstream `RecurringCharge` rows is re-targeted to the new active LC version.
*Sources: BE Tech Spec §4.5*

*Sources: BE Tech Spec §3.1; PRD FR-03*

**13.2** Plans with no eligible (rate-bearing) charges are skipped with reason `no_eligible_charges`.
*Sources: BE Tech Spec §3.1*

**13.3** Templates with no charge line items are excluded from Flow B.
*Sources: PRD FR-20; BE Tech Spec §3.2*
